## 项目工作台的操作流程

原概况只显示四个计数和一个笼统的“当前任务”，需要反复切换页签寻找场次；抽签和编排会离开工作台，操作后也容易丢失项目上下文。状态判断还把轮空算入待完成比赛，并对未生成配置、自动预览和手工赛程使用了不一致的下一步判断。

本轮将工作台组织成报名名单 → 分组与赛程 → 比赛记录／个人赛成绩录入 → 成绩与名次。进度入口随时可访问，页面根据后台正式记录推荐下一步，不用浏览器输入或单独保存的“完成度”代替业务状态。

- 概况显示可直接进入的流程入口、可记录场次、具体待办。资料缺项、可记录场次、小组排名待确认、场地时间待安排各有对应入口，不重复堆叠相同统计。
- 分组与赛程包含“比赛列表与场地”和“抽签与编排”两种操作。逐场录入保持可用；自动生成的预览需要管理员确认后才允许领取记录。
- 编排保存、生成、确认只刷新工作台内的内容，保留项目导航。比赛记录、比赛列表和编排中的记录入口都携带当前项目，返回列表时继续停留在该项目。
- 小组比赛结束而后续比赛等待排名时，首页提示核对具体小组；点击待办进入成绩页并定位该小组，不自动确认排名或生成结果。
- 实际比赛与轮空分别统计。个人赛分别统计未录入、后台保存待确认的成绩和已确认名次，避免只录入部分成绩就跳到已完成状态。
- 瑞士赛按后台计划轮数判断是否结束。当前轮确认后，待办定位对应阶段，由用户确认生成下一轮；全部计划轮次结束后才推荐确认最终排名。
- 三人赛不足三名队员时仍可报名，并提示资料待补充。切换甲乙丙组优先保留项目类型和性别；可用“全部项目”重新选择。

桌面采用比赛队列和待办两列，平板与手机自动叠放，进度和待办按钮保留完整点击区域。统计刷新及页面重新打开都读取后台；打开概况、待办或赛程页面本身不领取记录任务，不确认方案、抽签或名次。

EntryDesk 的借鉴限于操作入口和导航。本系统继续遵循后台保存的数据为准、普通表单不保存本机草稿、赛程与阵容分开保护的既有规则。

## 当前问题与本轮修复

原实现把报名主体、队员阵容和赛程变更统一交给 `guard_change`。一旦确认方案，项目卡片里的所有输入都被禁用，连新增学校人员也无法操作。这也与“队员资料可以赛前补齐”的提示相冲突。

现在区分三类修改：

| 修改 | 已确认赛程、该校场次尚未领取记录 | 该校已有场次领取记录或已有成绩、名次 |
| --- | --- | --- |
| 新增学校人员档案 | 允许；适合当前三人赛且有名额时，可一起加入项目 | 允许新增档案，界面明确说明只加入学校人员名单 |
| 已报名三人赛的队员、项目号码、队长 | 允许，保存后沿用原参赛记录及对阵 | 阵容冻结，显示具体原因 |
| 更改参赛学校、报名/退出状态、种子 | 需要先处理赛程 | 继续受报名与成绩保护 |
| 报名备注、人员区分信息、常用号码 | 允许维护 | 允许维护；不改变已记录阵容 |

个人赛更换参赛运动员属于更换报名主体，继续受报名保护；三人赛补录队员沿用原学校的参赛位置。球队最多 6 人、同一赛事不可兼项、学校/组别/性别匹配、队长必须在名单中等规则继续由后台校验。

操作仍是“添加人员并加入本项目 → 预览整批变更 → 确认整批提交”。添加或预览时不写正式名单，提交成功后重新读取后台数据。普通表单不保存浏览器草稿。

本轮没有自动解锁、重新抽签或重新编排。保存阵容时保留学校、球队和参赛记录 ID、种子、报名状态、固定分组及场次。预览后如有记录任务领取，提交会拒绝过期预览并返回后台最新状态。

## 后续功能设计的统一原则

- 学校报名负责人员档案和各项目完整名单；项目工作台负责参赛学校核对、赛程和成绩。
- 确认赛程固定参赛位置、分组、签位、场地和时间；进入比赛记录再保护对应学校的阵容。
- 按具体操作显示可编辑范围与原因，新增人员入口明确说明是加入学校名单还是加入当前项目。
- 涉及参赛主体或已记录比赛的更正应有专门流程、影响明细和审计，避免普通报名编辑改变历史记录。
- 页面展示及资格判断以后台保存的数据为准，提交过程中沿用并发校验、事务回滚和原请求重试。

本轮通过独立测试数据库验证赛程确认后的新增、名单与对阵保留、领取记录后的冻结、并发领取、错误提交回滚及既有资格规则，并检查桌面与手机的实际操作。

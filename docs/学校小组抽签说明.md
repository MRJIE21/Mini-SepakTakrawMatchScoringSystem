# 学校小组抽签

适用以学校为单位参加的三人赛项目，由管理员或已分配本赛事的编排与成绩人员操作。一个项目内每所学校只有一个参赛主体，分组直接按学校抽签。

## 现场操作

1. 打开三人赛项目工作台的“赛程安排”，点击“小组抽签”。展开名单核对学校及种子序号。
2. 选择“完全随机”或“种子分档”，设置小组数量。支持只分 1 组及每组 1 校，没有固定的 26 组上限。各组人数留空按人数均分，也可按 A、B、C…组顺序填写，例如 `2,1,1`；超过 Z 组后继续使用 AA、AB…组。各组人数须为正整数，合计等于报名学校数。
3. 点击“开始小组抽签”。可逐校点击“抽下一所学校”，也可“一键完成抽签”。“全屏展示”适合现场投屏，“退出全屏”返回页面。
4. 全部揭晓后核对并“确认抽签分组”。可打印正式分组表，或通过浏览器另存为 PDF。
5. 下方编排自动采用本次确认的分组。设置循环次数、每组晋级人数及淘汰赛规则，点击“保存并查看赛程预览”。核对场次、晋级路径、场地和时间，最后由管理员锁定方案。

抽签确认固定学校所属小组，赛程锁定固定比赛方案。抽签确认后还可以调整循环次数和晋级规则；重新生成赛程保持相同的小组成员与组内签位。
常用编排支持单组、单校小组及超过 26 组的分组。每组晋级人数不能超过该组学校数；单校小组需选择“前 1 名”。只有一校的小组不生成组内对阵，名次由组织者确认。至少分两组且每组前两名晋级时自动交叉配对，淘汰赛首轮避免同组相遇。

全屏和普通页面使用相同的浅色背景、白色小组卡片及揭晓区配色。揭晓区不再淡入，进入全屏、退出全屏及确认后返回页面均直接显示完整颜色。

## 两种抽签方式

| 方式 | 名单与名额要求 | 抽签规则 |
| --- | --- | --- |
| 完全随机 | 至少 1 组，各组名额为正整数且合计等于报名学校数 | 随机排列学校和全部组内名额，按名额分配；允许 `6,2,2`、`2,1,1` 等不等人数分组 |
| 种子分档 | 同上，并要求每校具有唯一正整数种子序号，各组人数最多相差 1 | 按种子序号从小到大分档，每档学校数等于小组数量；每组每档最多一校，最后一档可不足 |

种子序号在项目“报名名单”中编辑。例如 10 校分 3 组：种子 1—3 为第一档、4—6 为第二档、7—9 为第三档、10 为第四档；名额为 4、3、3。各档独立随机抽签。

## 保存与重抽

- 开始时由服务器生成一次固定抽签顺序，尚未揭晓的分配不会返回页面。揭晓进度实时保存，刷新或换设备可继续。
- 同一次操作重试沿用原请求标识；服务器已保存但响应丢失时，不会多抽一校。出现“操作结果待核实”可刷新状态，或用原操作重试。两台设备同时操作时，旧版本会提示刷新，不覆盖新进度。
- 需要重抽时点击“撤销本次抽签”，填写原因，再开始新抽签。“已撤销的抽签记录”保留最近的撤销记录、原因与已揭晓分组，后台审计保留操作人。
- 报名学校或种子序号发生变化后，旧抽签会失效，须撤销并重新核对。旧抽签编号不能继续保存、生成或锁定分组赛程。
- 方案已锁定时，先由管理员填写原因解锁才能调整；已有比赛成绩时禁止重新抽签或更改分组。撤销后须重新保存并生成赛程预览，旧预览不会直接作为新的正式赛程。

## 更新与实现

重启后端并联网刷新网页即可更新；启动时自动为已有赛事库补齐 `group_draws` 表，保留现有赛事数据。无需安装新依赖。

参考 [inker/draw](https://github.com/inker/draw) 的逐校揭晓与分组展示流程，抽签、持久化及页面均在现有 Python 标准库和原生 JavaScript 架构内实现。

- `app/domain/group_draw.py`：随机与分档分组，使用系统随机源。
- `app/api/group_draw.py`：抽签状态、版本冲突、请求重放、确认、撤销和分组表打印。
- `app/api/scheduling.py`：用已确认抽签的学校成员生成原有循环赛及后续晋级赛程，保存、生成、锁定时核对抽签。
- `web/js/groupDraw.js`：抽签操作、恢复、现场展示与历史记录。
- `web/js/views/scheduling.js`：确认分组与常用、高级编排流程衔接。

回归测试使用独立测试赛事和临时数据库，不修改正式赛事。接口测试位于 `tests/test_group_draw.py`，现场操作回归位于 `tests/group_draw.browser.test.mjs`，编排规则覆盖位于 `tests/scheduling_flow.test.mjs`。

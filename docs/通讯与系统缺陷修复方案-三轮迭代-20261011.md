# 通讯与系统缺陷修复方案：三轮迭代

日期：2026-10-11。范围：当前工作区的 HTTP 接入、数据库事务、账号跨库同步、列表与记录页面、正式成绩和派生名次。

这是三轮审查后形成的实施方案。本次没有修改产品代码，没有执行真实赛事的数据修复；下文的性能指标是待实现后验证的门槛，不是已达到的结果。

依据：[通讯负载与严重缺陷审计](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/docs/通讯负载与严重缺陷审计-20261011.md>)及其隔离复现脚本。当前已测得：100 并发轻请求有 32/200 拒连，30 并发全量记录队列 P95 为 15.40 秒，1000 场列表的序列化约 8001 次 SQL；成绩、草稿和跨库快照另有明确的正确性故障。

## 第二轮：否决或补强的方案

1. **否决“超时就视为提交失败”。** Abort、断连和响应解析失败不能证明数据库回滚。原包必须包含固定的 UID、base_version、赛事及部署身份，持久化后才能发送。此前已待核实的包，不能因后续 403、503 或暂时 found:false 被释放：它们只说明本次核对或重试的结果。服务端提供原提交者可用的只读收据核对入口，写操作仍执行当前权限检查。
2. **否决“新页面加 CAS 就够了”。** 已打开的旧页面仍会执行旧 put/remove。新草稿存储与旧存储隔离；升级被旧连接阻塞时停止新页写入并提供导出、关闭旧记录页、重载的路径；不得自动降级绕过存储升级。旧协议正式提交明确要求升级，保留旧草稿和待核实包。
3. **否决“删除草稿即可结束记录”。** 物理删除后，旧页迟到的保存会重新创建草稿。discard/finalize 写入持久的 generation、revision 与 terminal 标记；旧 generation 永远不能复活，冲突分支仍能导出。
4. **否决“在数据库取一页以后再做权限过滤”。** 权限条件先于 COUNT 与分页，否则 total 泄漏隐藏场次、可见页面漏行。赛程冲突检查、全阶段清空数量和合计也不能根据当前页推算。
5. **否决“账号同步异步化以后无需保障新用户”。** 新账号可能尚未出现在赛事库。赛事写事务确保 actor 及 transfer target 等被引用用户的快照存在；权限始终依据全局库，不依据延迟的赛事快照。
6. **否决“socket timeout 足以阻止慢请求”。** 每次读超时可以被持续滴入的数据重置。请求头、body 和响应写入需要单调时钟总期限，以及无进展期限；排队期限必须独立处理。
7. **否决“测试继续使用原 ThreadingHTTPServer”。** 生产、API 回归、浏览器夹具和压测使用同一 create_server 工厂，否则接入修复没有被测到。
8. **收缩改动范围。** 保留现有密码字段和 SQLite 架构；不引入消息队列服务、数据库替换或全站状态框架。不自动改写人工名次，不合并两个不同的计分草稿。

## 第三轮：实施顺序与最终约束

以下工作包按顺序推进。A、B、C 是数据正确性的前置门槛；D、E、F、G 降低卡顿与资源耗尽风险；H 将它们共同验收。

### A. 事务、正式更正与提交收据

入口：[db.py:148](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/db.py:148>)、[idempotency.py:40](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/idempotency.py:40>)、[scoring.py:540](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/api/scoring.py:540>)。

- 修复 db.tx 的 COMMIT 失败路径：仍在事务时尝试回滚，保留原异常，保证连接不带未结束事务回到工作线程。嵌套事务复用外层，不自行提前提交。
- 更正、取消、确认服务入口使用事务加内部唯一名称的 savepoint，HTTP 调用和直接 domain 调用都受保护。业务变化、版本递增、晋级/名次/积分重核、审计和 request_log 收据同一赛事事务提交。外层捕获异常后继续提交其他操作时，这条失败变更也必须已经完整回滚；不全局改变现有 db.tx 嵌套语义。
- 正式更正/取消包必须携带 request_uid 和加载时的 base_version；原计分端点沿用 submission_uid，按各端点约定冻结幂等 UID，不强行将已有计分协议改名。缺版本不填入当前版本替代。旧客户端得到明确的 client_upgrade_required，并保留输入供升级后核对。
- 计分、个人项目及正式更正的写入协议增加明确最小版本，与 C 的新存储同批启用；旧页不能继续发送绕过草稿代次保护的正式包。只读接口保持兼容。
- 幂等重放校验 user_id、action/path/match_id、event UUID、deployment 身份及完整冻结内容 hash；已有 UID 不同主体、范围或内容返回冲突。对合法重放先返回原收据，再由新 GET 刷新当前比赛，不因当前版本变大拒绝已经成功的原包。
- 新请求才比较 base_version。不匹配返回 409 version_conflict 和允许访问的当前结果；禁止自动改版本再次提交。
- 提供只读收据核对：只允许原提交者或明确有权的管理员访问，不向其他账号泄漏结果。取消归属或暂停账号后不能靠核对接口获得新的写权限；需要重新认证才能核对，无法认证时保留包供管理员核实。
- outcome=not_committed 仅在未进入业务事务或可证明完整回滚时返回。COMMIT 后响应失败，客户端按 unknown 保留包。同 UID/原内容有限重试，不能换 UID。

### B. 名次失效、有效比赛与重置赛生命周期

入口：[ranking.py:41](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/domain/ranking.py:41>)、[standings.py:147](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/api/standings.py:147>)、[standings.py:537](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/api/standings.py:537>)、[scoring.py:220](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/api/scoring.py:220>)。

- 已记录比赛结果作为正式名次与晋级依据时，必须 finished 且 result_status 属于 normal/home_forfeit/away_forfeit。cancelled/unfinished 的历史 sets 仅供审计；不从总分兜底生成有效冠军。结构上合法的 void 轮空单独解析唯一参赛者，只有胜者、无负者；inactive/review 重置赛不属于合法轮空。有效 normal 结果的局分仍使用现有规则。
- 小组退确认同时使快照待确认。只有 pool.confirmed 与 snapshot.confirmed 同时成立且确认依据仍有效，才能导出正式名次。更正、取消、重确认均在同事务内重核自动/小组来源名次与学校积分。
- 人工及个人项目名次保留来源，不静默覆盖；若与新结果冲突，显示待复核及原因，不继续把冲突自动名次当作确认结果计分。
- 快照比较使用项目排名，按 rank_no 排序。保存确认时的源输入指纹：已提交场次结果版本/result_status/记录时双方与局分、成员及 seed、抽签、排名参数、实际结构及签位源配置、确认范围。排除 pool.status、快照、placements/points、确认元数据、派生 ready/pending/void 和未记录场次的 actual；不直接依赖整个 plan.version。旧库缺少派生成员时先做一致性修复再产指纹，避免确认中的 refresh 改变基准。
- resolutions 只能完整、唯一地排列当前并列组，不能更改已经明确的非并列名次。保存人工并列顺序及其源指纹；相同依据下保持有效，依据变更才要求重确认。
- 重置赛建立 reset_parent_id、active/inactive/review 与父场次版本关系。当前父场次最多一个 active 重置赛；所有晋级解析、scoreability、refresh 和 derive 使用同一有效性条件。
- 条件失效且未领取、无得分/提交的重置赛可停用；已有 claim 也视为可能正在离线记录，需返回 409，列明场次、版本、记录员并要求显式复核处置。保留历史局分、提交和审计，inactive 不能以 void 形式重新变成轮空晋级。
- 父赛再次更正使条件恢复时，已有历史成绩的重置赛不自动变成有效冠军依据；显式复核旧结果或创建新的 active 场次。新重置赛属于父决赛的 stage，保留完整签位来源，不找方案的首个双淘汰阶段。

### C. 多页面草稿及升级

入口：[store.js:101](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/web/js/store.js:101>)、[store.js:142](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/web/js/store.js:142>)、[sw.js:3](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/web/sw.js:3>)。

- 新增独立的草稿存储 schema，保留旧副本。计分草稿在同一个 IndexedDB readwrite 事务中读取、比较 expected_revision/generation/terminal，再写入 revision+1；赛事缓存用独立 cachePut，不套用草稿冲突规则。
- 同一页面按 key 串行保存不可变快照，传递上次成功 revision；发送前 flush 并检查保存成功。review、individual 等入口也必须检查存储结果，不能忽略 put/remove 失败。
- CAS 冲突保留双方内容，提示暂停该页记录、选择权威草稿或导出核对；不自动相加、拼接或最后写入覆盖。Web Locks/BroadcastChannel 可用于提示和减少冲突，不能代替数据库原子校验。
- discard 和提交成功用事务写持久终结标记。回执只 finalize 原 generation，不错误终结同 key 新 generation；若服务器已确认 subject，其他记录内容原样保留为只读冲突分支并展示正式版本。放弃待核实记录可以离页但仍保留原 UID。旧页面、迟到的保存/回执和 BFCache 恢复都不能绕过终结。首版不做 tombstone 自动清理。
- 新 generation 只能在获取最新服务端 ready/base_version 后显式 beginDraft；expected_revision=0 不允许复活旧 generation。
- 旧 IDB 连接阻塞升级时给出保存/导出、关闭旧页、重载步骤，并停止新页写入。Service Worker 更新不足以升级正在运行的旧 JS；服务器的计分协议边界拒绝旧提交。不得强制重载未落盘的旧页面。
- 缺少可靠 IndexedDB 时：有可用且全部写入方遵守的 Web Locks 才能提供相应的原子存储；否则每页面保存不可变独立分支供恢复，并暂停共享草稿正式提交。局域网 HTTP 的能力必须实测，不能假定 Web Locks 一定存在。
- 降级分支每页使用独立随机 writer ID，不复用复制标签页的 sessionStorage 标识。本 writer 新版本写入并校验成功后才能清理自己的较早普通快照，未知包、其他 writer 和 legacy 副本不自动删除；配额失败必须返回未保存并提供导出。所有入口经统一存储适配器，不允许直接 IDB.put/localStorage.setItem 绕过校验。

### D. 有界接入、期限与请求资源回收

入口：[http_server.py:75](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/http_server.py:75>)、[http_server.py:267](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/http_server.py:267>)。

- 建立生产及测试共用 create_server；固定工作线程和有界 pending 队列，不为每连接、每期限创建新线程。初值：workers=32、pending=128、backlog=256；均可配置，必须在 H 中实测后定值。
- 第一阶段每连接处理一个请求并明确 Connection: close，覆盖成功、错误和超载路径。请求完成时事务已结束、结果已物化，再关闭线程数据库连接并发送；finish 作为兜底。静态文件与备份下载也有写期限，不能让慢读者长期占用工作线程。
- 排队入业务截止初值 5 秒；请求头绝对期限 3 秒、body 绝对期限 15 秒、无进展期限 3 秒、写期限初值 5 秒。头总量、请求体保留明确上限（body 4 MiB）。期限使用单调时钟，不因滴入一个字节重新开始总预算。
- pending 使用有界 FIFO deque+Condition，增加一个固定的过期回收线程。worker 领取与过期回收在同一短锁下将 QUEUED 原子转为 RUNNING 或 EXPIRED；过期连接脱队释放锁后非阻塞尽力写小型 503 并关闭。不能每连接起 Timer、仅在 dequeue 检查期限或在锁内阻塞写；32 个 slow-body 占满 worker 时，pending 仍须在 5 秒加有界调度误差内回收，且永不执行过期业务。不可写客户端不保证收到完整 503，但必须及时关闭。
- header 与完整 body 共用响应写入总期限，不因每块写入重置。下载服务器写期限初值 30 秒，客户端可取更长；32 个慢读者占满时允许受控拒绝，压力解除后须恢复，不能承诺慢请求占满时其他请求永不拒绝。
- HTTP 的数据库忙等待初值 1 秒、同步 worker 200 毫秒。只将已识别的 SQLITE_BUSY/LOCKED 映射为可恢复 503，附 Retry-After；不能掩盖 schema、权限或数据完整性异常。
- 观测 active workers、pending、排队等待、超期原因、连接数/DB 连接数、BUSY、响应时间与大小、进程内存。队列满时受控拒绝，不在调度路径执行耗时业务或等待数据库。

### E. 可恢复的账号跨库同步

入口：[db.py:124](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/app/db.py:124>)及 admin/auth/重置密码 CLI 的账号写入口。

- 全局账号新增单调 snapshot_revision。账号修改与目标赛事 outbox 同一全局库事务；请求不连接或等待任何赛事库。保留现有用户字段，迁移使用显式列映射，避免增加字段后 tuple(user) 与原 INSERT 列数不一致。
- outbox 按赛事与用户合并到最新 revision，保存 event UUID/deployment、尝试次数、next_attempt 和错误。后台单 worker：读已提交快照并释放全局读事务→赛事短写事务条件 upsert→全局短写事务确认；全过程不同时持两库事务。
- 赛事快照只接受更高 revision；确认只清理已应用版本，不删除执行期间新入队版本。退避 1/2/4…60 秒加抖动，单赛事失败不阻止其他任务。不存在或身份不匹配的赛事库不能被 connect 自动创建；明确失败状态供管理员查看。
- 首次迁移全量入队以修复旧半同步。创建新赛事复制当前快照及 revision；赛事备份恢复后重新核对身份和同步目标，不把恢复前的完成标记当成已完成修复。
- 赛事写操作在事务内确保 actor、transfer target 及实际外键引用用户的快照。不能将“快照尚未到达”显示为“账号停用”。新请求的权限和 active 判定始终读取全局库，延迟快照不能恢复已撤销的权限。
- 程序停止时先停止接入并结束请求，再停止同步 worker、由各线程关闭自己的连接。重启安全重复执行未确认任务，不承诺多库同时提交；全局修改已成功但部分赛事延迟应明确显示为“同步中”。
- 排队期间停用账号，在 worker 开始鉴权时必须按全局库拒绝；已经鉴权并开始的在途请求按事务完成，不承诺跨库瞬时撤销全部在途写入。停用的新 revision 已应用后，迟到的旧 active 快照与旧 ack 都不能恢复权限或删除新任务。

### F. 分页、批量序列化与统计

入口：common.serialize_match、matches/queue、scheduling 的方案详情，以及 scoring/matchAdmin/admin/review 页面。

- 显式 offset/limit，初值每页 100、max_limit=200，返回 matches/total/has_more/list_revision。排序与现有业务优先级一致，最后以 id 消除同值顺序不确定。筛选条件、当前权限 scope 先于 COUNT/LIMIT；不能对取出的页再做截断式可见性过滤。
- 每页 count、数据、revision 及关联序列化位于一个短读快照。下一页带上一页 revision；变更返回 409 list_changed 并重载，不把新版本页追加到旧版本。禁止跨翻页持数据库事务。revision 是成员/顺序版本，不是全部内容版本；使用赛事库单调整数及条件触发器，字段实际变化才递增。
- 维护一份过滤/排序与触发器依赖清单：matches 增删及相关状态/排程/归属，plans 可见性集合变化，groups/categories 的顺序，参与标签搜索的 schools/teams/athletes/participations 关联与显示字段。纯比分/result_version 或无关 updated_at 不影响成员/排序时不递增。最近成绩固定 30 条单页短快照，不加入普通分页 revision；未来若按 updated_at 连续分页，另设对应版本。不能用秒级 MAX(updated_at)、MAX(id) 或跨新连接的 PRAGMA data_version 充当 revision。
- 严格 revision 分页不能保证持续成员变更时完成遍历。保留筛选和操作草稿，最多自动重载一次；继续变化则提示用户刷新，不能无限跳第一页。频繁比赛期间优先有界实时页，不后台拼全量后宣称同一快照。本轮不实现跨请求固定 ID 列表快照；若必须持续遍历，另加有期限的专用快照。
- legacy 未声明分页的请求，只有 total 不超过兼容上限时才完整返回；超限返回 pagination_required，不能成功返回貌似完整的 100/500 条。所有页面和 Service Worker 缓存版本同批迁移。
- 批量预取 category/stage/pool/venue、双方标签、sets（按需）、ownership、提交作者、最近更正审计、pending 来源场次/小组快照。Map 只在一个请求中复用，不跨赛事、权限或版本缓存。
- 常规场次页的前置方案读取新增 include_matches=0/summary 形态，仅查方案、阶段及所需聚合，不先查询/序列化全部 matches；迁移 matchAdmin 等只需元数据的入口。bracket/results 确需图结构时明确完整或按 stage 契约，采用批量序列化，不能被普通列表分页静默截断。
- 记录队列保留 ready 等现有优先顺序，筛选/搜索改变时重置页；最近成绩由服务器按 updated_at/id 倒序取 30 条，不再逐项目默认截断后拼装。
- 赛程冲突预检由服务器检查完整范围，提交仍事务内执行权威检查。全阶段清空的确认数量从服务端 summary 获取，并在写事务中复核范围/版本后返回实际删除数；不能把当前页数量用于全阶段操作。
- 全量导出使用专用服务端路径，在受控读快照内形成结果后释放 DB；阶段/赛事统计使用服务端聚合，不在前端累加当前页。
- 多查询 GET 用短读事务，授权过滤和结果物化包含在内；backup GET 目前含审计写入，需拆分读取/备份和短审计写事务，不机械地把所有 GET 包成只读事务。

### G. 请求期限、导航和待核实恢复

入口：[api.js:32](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/web/js/api.js:32>)、[main.js:140](<E:/Sepak Takraw Competition Scoring System/sepak-takraw-scoring-system/web/js/main.js:140>)、pendingRequests、scoring/review/individual/admin。

- API 支持 signal、timeoutMs 和冻结赛事上下文；计时直到 body/blob 完成并通过预期结构校验。非法 200、缺少必要成功收据不能当成提交成功。
- 写包在 await 本地保存之前冻结账号 ID、赛事/部署身份；保存后发送仍使用原包 context，不能重新读取当前页面赛事。账号已切换时只保留原账号包，不用新账号发出。回执校验 uid/kind/subject/status/hash 与正式版本，定义 duplicate 合法回执形态后才能 finalize。
- 区分主动导航取消、读取超时、网络不可达、业务冲突和提交待核实；用户可看见恢复路径。GET 可有限重试；写请求不自动生成新 UID或修改包。
- GET 期限示例 10 秒、写请求 30 秒、下载 60 秒，均为待调参数；依据 D 的排队/执行预算和实测 P99 调整，不能把前端到期解释成服务器事务取消。
- 离页检查完成后取消旧 render 的 GET；每次 render 带独立 generation、signal、冻结身份和容器。旧响应不能修改新页面 DOM、赛事结构缓存或错误提示；loadStructure 等全局写入也需代次检查。
- 旧 render 的 catch、leaveGuard 注册、reloadShell/recoverIfOffline 和页内筛选刷新也检查各自 generation；不只保护成功 DOM 分支。同步 JSON.parse 不能被 AbortController 抢占，靠有界分页与响应字节上限减少主线程卡顿，不宣称超时能中断同步解析。
- 路由不取消已经发出的 POST。正式包先可靠落盘再发送；超时后允许离页，但包保持待核实。核实成功才 finalize 对应 generation；未知包不能因刷新、换赛事、恢复登录或存储失败消失。
- 网络恢复后用原 UID/原内容核对。查询暂未找到不能解冻原包；支持管理员核对、导出与明确解决待核实状态，不无限轮询或换 UID重复写入。

已有 192 项 Python 回归和 9 个前端规则测试重新执行；新增只覆盖这次缺陷与失败边界。真实浏览器两页、旧页升级、HTTP期限/丢响应测试不可由 mock 单测代替。全部 HTTP测试使用产品工厂。所有试验继续使用隔离数据及随机本机端口，不对真实赛事压测。

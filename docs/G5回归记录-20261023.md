## 6 停服恢复演练（第三轮）

方法：服务运行中先做一次 `backup` + `verify`；随后**停止服务**，在确认没有新账号/赛事身份变化的前提下备份，直接用 SQLite 修改 `schools.name` 模拟误改，再用 `restore --yes` 恢复，重启后核对数据。

| 步骤 | 结果 |
| --- | --- |
| backup（运行中） | `backup-20261023-104750`，registry + event_1，`integrity=ok`，关键计数：users=4、matches=2、result_candidates=1、audit_logs=25 |
| verify | 通过，列出各库 sha256 与关键表计数 |
| 保护性拒绝（两次） | 备份后新增“临时事件”或改名导致 `users.snapshot_revision` / `events` 变化时，restore 返回 exit 1：“禁止回退独立复核账号/权限真源：users / event identity”；证明恢复不会吞掉更新的权限与赛事身份事实 |
| 停服 + 误改 + 恢复 | 停服后备份 `backup-20261023-105016`；SQLite 离线把学校名改为“停机误改标记”；`restore --yes` → “已恢复数据库文件 3 个，恢复前快照 pre-restore-…”，exit 0 |
| 重启核对 | 学校名恢复为备份时名称；`result_candidates` 1 条、审计日志可读；事件与抽签数据完整 |

结论：停服恢复可用且带保护；**恢复前必须先停服、备份须包含当前权限状态**（服务运行中 `/api/login` 会改变 users 行，导致恢复被安全拒绝）。

# 报名流程重构建议

调研日期：2026-10-06。

本方案根据重构前的代码静态核对补齐实施约定。2026-10-06 已实现第一期工作台及统一提交闭环，第二期补齐学校级表格导入与共享草稿，实际交付范围和验证见 [学校报名工作台实施记录](学校报名工作台实施记录.md)。下文“当前基础”保留调研时的状态，后续扩展仍按方案分期实施。

建议以学校为主要报名入口：一次整理本校人员，在同一个工作台分配各项目，统一核对后提交。项目工作台保留项目名单和快捷补报入口。以下界面和提交方案是针对本系统提出的设计；来源项目的实际能力另列。

## 当前问题

截图中的个人赛报名下拉框主要展示已报团体项目、不可兼项的运动员，并同时出现下拉框滚动和弹窗滚动。用户选择了学校后，仍要逐条读重复说明才能判断是否有人可报名。

当前代码中，人员档案、项目名单和参赛记录已经分开存储，但入口主要按单个项目组织。学校提交完整报名名单时需要反复切换项目，重复选择学校。

现有依据：`web/js/views/catalog.js`、`web/js/views/workspace.js`、`app/api/catalog.py`、`app/schema.sql`。当前新增报名执行个人项目每校限报 1 人、三人赛每队最多 6 人，以及赛事内运动员不可跨项目兼项；实际比赛规则调整须另行核对赛事规程。

### 当前基础与已确认缺口

| 能力 | 当前实现 | 首期工作 |
| --- | --- | --- |
| 学校详情聚合 | `GET /api/schools/{id}/detail` 聚合人员、阵容及个人报名 | 扩展学校工作台数据 |
| 人员、阵容、报名分离 | 对应数据表及稳定 ID 已存在 | 保留现有关系和 ID |
| 导入预览与整批提交 | `app/api/imports.py` 的 CSV 导入有状态摘要核对；正式提交有错误时整批回滚 | 扩展至学校级完整变更 |
| 部分成功批量加入 | `batch_participations` 使用每项保存点，允许部分成功 | 保留独立语义；学校级提交采用整批原子语义 |
| 请求重放 | `app/idempotency.py` 按请求标识及内容哈希重放 | 新接口复用，并纳入赛事及学校身份 |
| 草稿 | `web/js/drafts.js` 在本机按账号和赛事隔离保存 | 首期继续使用本机草稿 |
| 更新阵容与恢复报名 | `update_team` 重写成员没有校验跨项目兼项；`update_participation` 恢复 `active` 没有重新校验兼项或学校名额 | 优先补齐，所有入口共用最终状态校验 |

现有 `_guard_plan_state` 仅在部分组合报名入口使用，判断方案为 `locked/running` 且已存在场次。不能把它视为所有编辑、恢复和导入入口已经具有一致的变更保护。

## 首期使用者与范围

- 使用者为组委会管理员和组织者，按学校集中录入，沿用现有角色及赛事访问权限。
- 工作台范围固定为本届赛事、所选学校当前所属组别；服务端核对赛事身份、学校及组别归属。
- 学校自助登录、报名截止控制、跨设备协作、跨届人员库和一校多组别不纳入首期。
- 各项目从当前组别配置生成，默认可展示男子三人赛、男子个人赛、女子三人赛、女子个人赛。

## 建议的工作台

入口：赛事 → 学校报名 → 选择或新增学校 → 学校报名工作台。

页面顶部固定显示学校、组别、报名完成情况，主体提供“人员名单”“项目报名”“核对提交”三个可随时切换的页签。已有学校默认打开“项目报名”，无需依次完成三个页签。在项目分配中也能就地新增人员。桌面使用表格和分栏，手机使用项目卡片；长名单在工作台内编辑。

### 人员名单

- 首期一行一人，连续新增；后续扩展粘贴 Excel 和学校级 CSV 导入。
- 显示姓名、性别、常用号码、区分信息和已分配项目。本项目报名号码在项目阵容中编辑，不回写常用号码。
- 系统 ID 自动管理；可考虑增加学号或校内人员编号，用于明确匹配已有人员。
- 同名核对使用完整人员名单，包括已报其他项目或不符合当前项目资格的人员；普通选人列表的筛选不能改变身份核对范围。
- 本工作台新增或修改的人员先进入本机草稿，随学校级确认一并写入。提交失败时，本次人员修改及报名修改全部回滚。
- 原有档案入口仍可独立即时保存，明确标注“保存人员档案”，这类已保存数据不属于随后学校提交的回滚范围。

### 项目报名

按当前组别配置生成项目卡片；学校明确不参加的项目可标记“不参加”。

- 三人赛：可报名人员列表与已选阵容同时显示；直接编辑号码和队长。
- 个人赛：显示本校该项目名额和已选运动员；默认只列符合资格、未占用的人员。
- 不符合资格的人员收进“查看不可报名人员（人数）”，展开后显示具体原因。
- 无可报名人员时直接显示原因、查看已有报名和新增人员入口。
- 搜索承担筛选作用；新增人员作为明确操作，不要求用户滚动长下拉框寻找。
- 调整项目归属时按草稿中的最终分配展示可选性。例如先把甲从三人赛移出后，可以在同一份草稿中分配到个人赛；服务端仍以最终完整状态为准。
- 项目中就地新增人员后直接加入本次待提交分配，学校视图和项目视图继续使用同一份人员身份。

### 核对提交

提交前展示本校各项目的人数、运动员、队长、号码和待补充项，以及本次新增、修改和退出的明细。

核对结果分为阻止提交的错误、允许报名但需要补齐的资料、明确不参加的项目。当前允许三人赛先报名再补齐队员或队长；规则允许暂缺的资料不能被新工作台一律升级为阻止报名。

| 状态维度 | 表达方式 |
| --- | --- |
| 正式参赛记录 | 沿用 `active/withdrawn`，只有正式提交成功才更新统计 |
| 学校项目选择 | 待填写、参加、不参加；保存明确不参加的决定，不用缺失参赛记录推断 |
| 资料完整度 | 完整或列出待补项，与是否已报名独立 |
| 本机编辑状态 | 未修改、草稿、待核对、提交中、提交成功或失败 |
| 项目可变更状态 | 来自方案锁定、场次及成绩引用，不由学校报名完成状态推断 |

学校可显示“已报名 3 项、1 项不参加、2 处资料待补”。只有每个配置项目都已有正式报名或已保存“不参加”决定，才表示学校已完成项目选择；资料待补仍单独提示。

资格错误定位到具体人和项目。允许在草稿中保留冲突以便调整；正式确认必须通过后端校验。

## 学校级提交约定

### 验证最终完整状态

学校级请求携带一份完整变更。每个受影响项目提交调整后的完整人员和阵容，而不是分别调用退出和新增接口。服务端将这份变更覆盖到当前赛事快照上，计算最终状态后统一验证：人员身份、学校和组别归属、性别、人数、号码、队长、个人项目学校名额及跨项目兼项。

例如“甲从三人赛移至个人赛，乙补进三人赛”必须在同一次提交内验证、写入；验证时允许移走的人员释放其原项目占用。恢复已退出人员也按最终状态重新核对资格。

- 请求中未出现的项目保持原状。
- 退出必须明确指定；学校导入文件中没有出现的项目也保持原状。
- 阵容变更使用完整最终成员列表；预览展示被移出的成员，避免把漏填成员解释为无提示删除。
- 已有参赛记录尽量原位更新。跨项目移动保留原项目退出记录；目标项目复用该人员已有的参赛记录，只有不存在时才新建，不把旧记录 ID 改挂到另一项目。
- 人员、报名、阵容、明确不参加的决定和成功请求记录在同一事务写入；任一错误整批回滚。
- 学校级写入不复用允许部分成功的批量加入接口的提交方式。

### 统一预览和确认

建议新增以下接口，具体路径可在实现时按现有路由规范确定：

| 接口 | 职责 |
| --- | --- |
| `GET /api/schools/{id}/registration-workspace` | 返回完整人员、项目配置、当前报名、项目选择及基线版本 |
| `POST /api/schools/{id}/registration-preview` | 根据完整变更投影最终状态，返回新增、修改、退出、恢复及资料缺项明细 |
| `POST /api/schools/{id}/registration-commit` | 核对预览摘要及最新状态，重新执行相同业务校验，原子写入 |

预览不保存正式人员或报名。摘要绑定账号、部署和赛事身份、学校、组别、提交内容，以及受影响人员、阵容、报名、名额占用、项目配置、方案状态和成绩引用。新增记录造成的变化也应被检测，不能只比较已有行的 `rev`。

校验统一放到报名业务层，学校预览、学校确认、项目新增、阵容编辑、退出恢复、CSV 导入及批量加入共用。批量加入可以保留部分成功的产品语义，但每项仍必须使用同一组规则。

### 变更保护

| 变更 | 普通报名入口的首期约定 |
| --- | --- |
| 新增、退出、恢复、跨项目移人、阵容成员或种子改变 | 没有受保护赛程或成绩引用时，验证最终状态后提交 |
| 常用号码、人员备注等独立档案信息 | 核对档案版本，按已有资料维护权限保存；不改变项目报名号码 |
| 队长、本项目号码等阵容内容 | 纳入阵容版本；涉及已锁定比赛资料时进入受控变更 |
| 已锁定或运行且已生成场次的项目发生报名结构变化 | 普通入口阻止，展示影响；无成绩引用时可按既有权限解锁并重新核对编排，不能后台自动解锁 |
| 已有成绩或名次引用的身份、阵容和参赛结构变化 | 普通入口阻止，进入明确授权、记录原因和影响的更正流程；保留引用和审计 |

这些是待实施的一致规则。现有更正接口是否覆盖各类报名变更需在业务层实现时逐项核对；未支持的受控变更明确阻止并说明原因。

### 草稿、并发和重试

首期草稿保存在本机，明确提示“仅保存在本设备”。按账号、部署、赛事、学校和组别隔离，保存输入及打开时的服务器基线；恢复草稿后先重新获取服务器状态并比较差异。换设备续填及多人共享草稿需要服务端草稿能力，后续单独实施。

学校页提交时检查受影响人员、阵容、参赛记录以及其他入口导致的名额占用、项目锁定和成绩引用变化。项目页补报后，学校页提交应返回冲突明细和最新状态，保留用户输入；用户选择重载、合并或放弃本次改动，不能静默覆盖。

相同内容重试沿用原请求标识；更改内容后生成新标识。响应丢失时先核实原提交或原样重放，不以新标识猜测重试。预览失效后需要重新核对，新的确认内容使用新标识。

## 项目工作台的衔接

项目页继续展示正式名单、种子、编排及成绩。快捷补报使用可报名人员列表，并提供进入该学校工作台的入口。学校视图与项目视图引用同一份人员和报名记录。

现有导入以一个项目为单位。新增学校级导入时，模板应增加项目列，并让一份学校报名表覆盖多个项目；先预览完整变化，再统一提交。

## 实施顺序与验收

可沿用现有 `schools`、`school_entries`、`athletes`、`teams`、`team_members`、`participations` 关系，继续保留已有 ID。明确“不参加”的学校项目决定需要服务端持久化和版本字段；可新增按学校与项目唯一的决定表。本机草稿状态不写入正式报名记录。校内编号或后续服务端共享草稿通过单独迁移补充。

1. 修复当前选人体验：可报名优先、不可报名折叠、明确空状态和独立新增入口，同名核对继续读取完整人员名单。
2. 统一业务校验并覆盖编辑、恢复和导入入口，落实草稿、退出、恢复及锁定后的变更规则。
3. 交付学校工作台、连续录入、项目分配、学校级预览和原子提交的完整闭环。
4. 扩展 Excel 粘贴、学校多项目导入；学校自助报名和跨设备协作另行设计。

现有项目报名入口在切换期间继续提供服务，必须先补齐共享业务规则。

验收场景：

- 甲从三人赛移至个人赛，同时乙补入三人赛，一次提交成功；任一错误整批不落库。
- 已退出人员恢复时重新检查兼项、学校名额和项目可变更状态。
- 学校页与项目页并发修改时返回具体冲突，保留输入，不互相覆盖。
- 同名人员即使被选人列表隐藏，身份核对仍能发现完整候选。
- 明确不参加可以完成项目选择；资料待补与正式报名状态分别显示。
- 请求及导入中未出现的项目保持原状，退出必须明确指定。
- 原有档案入口已即时保存的人员不回滚；工作台本次待提交人员和报名失败时一起回滚。
- 响应丢失后原样重试只写入一次；改动内容使用新请求标识。
- 草稿恢复核对服务器基线；跨账号或赛事不串用草稿。
- 锁定赛程、已确认成绩及名次引用的受控变更不能被新旧入口绕过。
- 项目数量和名称由配置生成，常用号码与项目报名号码不互相覆盖。

同时记录一校完整报名所需操作次数，检查桌面与手机布局、无可报名人员及长名单的操作体验。
